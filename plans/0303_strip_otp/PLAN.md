# Plan: Strip OTP code from magic-link email

GoTrue's default magic-link email exposes a six-digit OTP token the user cannot
act on (Cairn has no code-entry screen) and that creates a social-engineering
attack surface. This plan removes the token by supplying a custom HTML template,
mounts it into the dev stack, and adds a Playwright assertion so the contract is
machine-verified before the first production deploy (step 14).

## Context

GoTrue v2.x sends two MIME parts in every magic-link email: an HTML part and a
plain-text fallback. Both are rendered from Go `text/template` sources that ship
inside the GoTrue binary. The default magic-link template includes both
`{{ .ConfirmationURL }}` (the link Cairn's sign-in flow relies on) and
`{{ .Token }}` (a six-digit OTP). GoTrue exposes
`GOTRUE_MAILER_TEMPLATES_MAGIC_LINK` to override the HTML template with a
file path inside the container; the plain-text part is generated by stripping
HTML tags from whichever HTML body was rendered.

Cairn's e2e suite already polls Mailpit via `waitForMagicLink()` in
`web/e2e/helpers/mailpit.ts`. That helper currently returns only the extracted
link URL. The Mailpit `/api/v1/message/{id}` endpoint returns both `HTML` and
`Text` fields, so extending the helper to surface both is a one-field addition.

## Decisions

**Single HTML file, no separate text template.** GoTrue v2 derives the
plain-text body from the HTML template by stripping tags. A separate
`magic_link.txt` would mean two files to keep in sync across GoTrue upgrades.
Since R3's constraint (no token in the text part) is satisfied structurally by
the HTML file never including `{{ .Token }}`, a text file adds maintenance cost
with no benefit.

**Return type change on `waitForMagicLink`, not a new sibling function.**
The happy-path test needs both the link URL (to navigate the browser) and the
raw email bodies (to assert OTP absence). Adding a second call to Mailpit for
the same message would be wasteful and would require another polling loop.
Changing the return type from `Promise<string>` to `Promise<{ link: string; html:
string; text: string }>` is cleaner; there is exactly one call site to update
(`auth.spec.ts` line 23).

**`\b\d{6}\b` as the OTP detector.** A six-digit sequence bounded by word
boundaries catches the GoTrue default token format (`000000`–`999999`) without
false-positives on longer numeric strings (e.g. port numbers or JWT fragments
that happen to appear in the URL). The regex is intentionally conservative —
false negatives (tokens formatted differently) are not a concern because we
control the template.

## Architecture

### New files

- **`gotrue/templates/magic_link.html`** — minimal HTML email template; uses
  `{{ .ConfirmationURL }}` only, brand name "Cairn", British English ignore note.

### Modified files

- **`docker-compose.yml`** — add `volumes` block to the `gotrue` service
  (`./gotrue/templates:/gotrue/templates:ro`) and
  `GOTRUE_MAILER_TEMPLATES_MAGIC_LINK` env var pointing to the in-container path.
- **`web/e2e/helpers/mailpit.ts`** — extend `MailpitMessage` with `Text: string`;
  change `waitForMagicLink` return type to `{ link: string; html: string; text: string }`.
- **`web/e2e/auth.spec.ts`** — destructure `{ link, html, text }` from
  `waitForMagicLink`; add `\b\d{6}\b` assertions on both bodies.

## Phase structure

1. **Phase 1 — template file and stack wiring.** Create
   `gotrue/templates/magic_link.html` and update `docker-compose.yml`. No test
   changes in this phase — the stack works correctly after `docker compose up
   --force-recreate gotrue`, but the machine-verifiable OTP assertion is not
   written until Phase 2.

2. **Phase 2 — Playwright assertion (RED → GREEN).** Extend the Mailpit helper
   and add the OTP-absence assertions to `auth.spec.ts`. RED: write the
   assertions first and confirm they compile. GREEN: the assertions pass against
   the already-configured stack from Phase 1. The `\b\d{6}\b` check is the
   machine-verifiable contract that the template change is effective.

## Phase 3 — Fix template delivery (GoTrue fetches over HTTP, not filesystem; localhost is not the host)

Phase 1 mounted `gotrue/templates/` into the GoTrue container and pointed
`GOTRUE_MAILER_TEMPLATES_MAGIC_LINK` at the in-container path. This never
worked: GoTrue treats the env var value as a **URL**, not a file path. When
the value starts with `/`, GoTrue prepends `GOTRUE_SITE_URL` and issues an
HTTP GET — e.g. `GET http://localhost:5173/gotrue/templates/magic_link.html`.
The container logs confirm the failure (`Error loading template … connection
refused`) and GoTrue fell back to its built-in default, which still includes
the OTP.

Phase 3 has two sub-problems that were discovered sequentially:

**Sub-problem A — filesystem paths.** GoTrue treats
`GOTRUE_MAILER_TEMPLATES_MAGIC_LINK` as a URL, not a file path. When the value
starts with `/`, GoTrue prepends `GOTRUE_SITE_URL` and issues an HTTP GET. The
Phase 1 volume mount was never read; GoTrue fell back to its built-in default
every time. This is confirmed by reading
[`mailme/mailme.go`](https://github.com/supabase/mailme) in the GoTrue
dependency tree — the fetch is unconditionally `http.Client.Get(url)`.

Moving the template to `web/static/gotrue/templates/magic_link.html` and
removing the volume mount (Task 3.1) fixed sub-problem A.

**Sub-problem B — Docker networking.** With the template at `web/static/`, the
env var `/gotrue/templates/magic_link.html` becomes
`http://localhost:5173/gotrue/templates/magic_link.html` after GoTrue prepends
`GOTRUE_SITE_URL`. But inside a Docker container, `localhost` resolves to the
container itself, not the host machine. `pnpm dev` runs on the host; the GoTrue
container cannot reach it at `localhost:5173`.

The fix is a dedicated `static` sidecar service (`nginx:alpine`) in
`docker-compose.yml` that serves `./web/static/` from within the Compose
network. The env var is changed to the full URL
`http://static/gotrue/templates/magic_link.html` (starting with `http`, so
GoTrue uses it verbatim without prepending `GOTRUE_SITE_URL`). The sidecar is
always reachable regardless of whether `pnpm dev` is running (Task 3.2).

This also corrects R2 in `REQUIREMENTS.md`, which described the SvelteKit
serving approach as the intended design.

## Phase 4 — Email-client compatibility

Mailpit's HTML checker flagged the initial template at 84% compatibility.
The problems were CSS properties that email clients strip or ignore: body-level
styles, `display:inline-block`, `background` on `<a>`, `border-radius`,
`margin` for spacing, and `font-weight:bold` without a tag fallback.

The fix is a rewrite of `magic_link.html` following email-safe HTML conventions
(documented in `docs/email-html.md`):

- Table-based layout replaces all CSS layout properties.
- `<td>` `padding` replaces `margin` for spacing.
- `bgcolor` attribute on `<td>` replaces CSS `background` on the button `<a>`.
- The button is a nested `<table>` — no `display:inline-block`.
- `<b>` replaces `font-weight:bold`.
- `font-family` and `color` moved off `<body>` to the wrapper `<td>`.
- `border-radius` removed (degrades to square corners in Outlook; acceptable).

Result: 95% Mailpit HTML check score. The remaining 5% is the `<body>` element
warning (structural — all webmail clients replace `<body>` with a `<div>`, so
even a bare `<body>` flags) and `margin:0` on `<h2>` (cosmetic degradation
only). Neither is fixable without removing content or adding VML hacks.
