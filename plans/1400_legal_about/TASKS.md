**Created:** 2026-10-20T13:37:50Z
**Completed:** 2026-10-20T13:51:37Z

**Why:** Container logs currently grow without limit, so the privacy policy can't state any retention. A size cap is the cheapest fix that makes a retention statement true.

**Prerequisites:** Task 0.2 (`logging.md` already describes the cap).

**Decisions:**

- Define one anchor at the top of `docker-compose.prod.yml`:
  ```yaml
  x-logging: &default-logging
    driver: json-file
    options:
      max-size: "10m"
      max-file: "5"
  ```
  Apply `logging: *default-logging` to **every** service in the merged prod stack. The prod overlay only lists some services (postgres, gotrue, auth-proxy, web, caddy). The base `docker-compose.yml` also has postgrest, sidecar and avatars, so add a stub entry with just `logging:` for any service the overlay doesn't list yet.
- Don't touch `docker-compose.yml` (the prod-safe base, shared with dev) or the dev override. Dev logs stay uncapped.
- **This is prod-facing.** The caps apply only when containers are recreated (`docker compose ... up -d`), and recreating a container discards its existing log file. Say so in the commit message body and in `docs/deployment.md`.

### [x] 1.2 Audit what the logs actually contain

**Created:** 2026-10-20T13:37:50Z
**Completed:** 2026-10-20T14:45:52Z

**Why:** The privacy policy must describe real log contents. `docs/logging.md` is a design that was never verified. The known suspects:

- GoTrue's request logger records `remote_addr`.
- Caddy's `reverse_proxy` adds `X-Forwarded-For` by default, which upstream services may log.
- The sidecar may log request metadata.

**Prerequisites:** Task 1.1.

**Decisions:**

- Check two things: (a) **observed** dev-stack logs after exercising real flows, and (b) **code and config reading** of the prod path, because in dev every client IP is a Docker-bridge or loopback address, so dev logs can't show whether real IPs would leak.
- Look for:
  - IPv4/IPv6 addresses that aren't loopback or private-bridge;
  - e-mail-shaped strings;
  - usernames used in the test run;
  - passwords and codes;
  - JWTs (`eyJ`);
  - query strings.
- For the prod path, read:
  - `caddy/Caddyfile.prod`: which upstreams get `X-Forwarded-For` / `X-Real-IP`; any `trusted_proxies`; any `log` directive;
  - `auth-proxy/src/**`: whether it forwards XFF to GoTrue, and what it logs;
  - GoTrue's configured log level and fields: `GOTRUE_LOG_LEVEL` in the compose files. Does GoTrue honour XFF for `remote_addr`? Check the GoTrue version's source or docs if needed;
  - `sidecar/src/**` logging;
  - PostgREST's log level and format.
- **STOP condition.** If real client IPs, e-mail addresses or usernames would land in any prod log, **stop, report to the user, and do not mark this task done**. The remedy (strip XFF before GoTrue, lower GoTrue's log level, or disclose a size-capped retention of IPs) is the operator's call. Don't word the policy around it.
- If clean, record the findings: what each service logs, and confirmation that no IP, e-mail or username reaches a log. Put them in `docs/logging.md` (replacing the "Audit: pending" stub) and in the logs row of the `docs/legal.md` claims table.

**Notes:**

- **The STOP condition was hit and resolved with the user.** Three findings came out of the dev-stack probes, which sent requests with `203.0.113.7` in the forwarding headers:
  - **GoTrue copies `X-Forwarded-For` / `X-Real-IP` into `remote_addr`.** The auth-proxy's generic pass-through forwarded both headers, so any request reaching it (for example `GET /auth/refresh`, because Caddy's `/auth/refresh*` route accepts every method) would log a real client IP.
  - **Postgres repeats row contents** in the `DETAIL` of constraint-violation errors.
  - **PostgREST's request lines carry the full query string and the User-Agent.** It logs Caddy's address, not the client's.
- **The user chose the fixes**, and they were made here:
  - `x-forwarded-for`, `x-real-ip` and `forwarded` are added to `SKIP_REQUEST_HEADERS` in `auth-proxy/src/index.ts`, covered by the new test `(h)` in `auth-proxy/test/shim.test.ts`. It was confirmed red, then green; all 96 auth-proxy tests pass.
  - Postgres runs with `command: ["postgres", "-c", "log_error_verbosity=terse"]` in the base `docker-compose.yml`.
  - `PGRST_LOG_LEVEL: crit` is set in the base `docker-compose.yml`.

  Both compose settings are re-verified on the recreated dev services: the `DETAIL` line is gone from the server log, and PostgREST prints no request lines. pgTAP still passes (805 tests).

- **Not done:** limiting Caddy's `/auth/refresh*` and `/auth/signout*` routes to POST. With the headers stripped it isn't needed for privacy.
- **Doc corrections found by the audit:**
  - slow-query logging is off (`log_min_duration_statement = -1`), not set to 1 s;
  - PostgREST didn't log one line per request;
  - the sidecar doesn't log upload attempts;
  - Postgres and PostgREST write plain text, not JSON.
- **Prod-facing.** The three fixes take effect on the next prod deploy: rebuild auth-proxy, then `up -d` to recreate postgres and postgrest.
