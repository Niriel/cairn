# Concerns — plans/0010_db_foundation.md

Generated 2026-05-08.

1. [ ] **`bootstrap.sql` lives in `db/tests/`, where `pg_prove` will pick it up as a test file.** `scripts/test-db.sh` invokes `pg_prove --ext .sql ... /db/tests`; even without `--recurse`, `bootstrap.sql` is in the directory pg_prove targets directly. With no `plan(N)` / `pass()`, pg_prove will treat it as a TAP failure ("no tests run" or parse error) and the whole suite goes red — Phase A's first run never gets off the ground.
   - Proposed: move it to a sibling location pg_prove won't enumerate (e.g. `db/test-bootstrap.sql` or `db/tests-setup/bootstrap.sql`) and update the path in `scripts/test-db.sh`.

2. [ ] **`triggers_set_attribution.sql`'s INSERT-time `deleted_by := NULL` test uses a UUID (`'11111111-…'`) that doesn't exist in `auth.users`.** The `deleted_by` FK references `auth.users(id)`, so the INSERT fails the FK constraint *before* the BEFORE trigger override runs. The test ends up exercising FK rejection of an unknown user UUID, not the trigger's NULL override that Risk #11 identifies as load-bearing.
   - Proposed: use a UUID that exists in `auth.users` for the test value — Bob's `bbbb…` from the `users_alice_bob_carol.sql` fixture, or the tombstone UUID. Update the test description in the plan accordingly.

3. [ ] **`triggers_profile_on_signup.sql`'s "direct skip-branch assertion" can't run as written.** It says: "DELETE the tombstone profile row, INSERT into auth.users with `id = '00000000-…'`, assert profiles is empty for that id." But step 3 of the migration already inserted the tombstone into `auth.users`; the second INSERT violates the PK. Profile-side delete doesn't cascade upward to `auth.users`.
   - Proposed: have the test `DELETE FROM auth.users WHERE id = tombstone` (which cascades to profiles via `profiles.id ... ON DELETE CASCADE`), then INSERT into `auth.users`, then assert `public.profiles` has zero rows for the tombstone id. Adjust the prose in the plan's `triggers_profile_on_signup.sql` row.

4. [ ] **PostgREST schema-cache reload is not addressed for the post-migration manual API check.** After `scripts/migrate.sh` applies `0004`, the running PostgREST container's cached schema is stale; the Verification section's `curl -i http://localhost:3000/profiles` will return 404 / behave inconsistently until the container is bounced or the cache is reloaded. PostgREST v12 supports `NOTIFY pgrst, 'reload schema'`, which is one statement.
   - Proposed: **dual fix.** (a) Plan-side: append a `NOTIFY pgrst, 'reload schema'` to `scripts/migrate.sh` after a successful migration apply. (b) Doc-side: add a one-line note to `docs/development.md` (in the migrations section) saying that `migrate.sh` issues the notify so PostgREST picks up the new schema without a container bounce — the hazard recurs for every future migration, so a doc-level convention saves future plans from re-discovering it.

5. [ ] **The migration's tombstone `INSERT INTO auth.users (id, email) VALUES (...)` could fail against real GoTrue's schema.** The plan acknowledges for `dev_seed.sql` that GoTrue's `users` table has version-dependent NOT-NULL columns without defaults and refuses to hand-craft rows there, but the same pattern is what step 3 of `0004` does. The bootstrap stub only carries `(id, email, role, created_at)`, so the test path can't surface a divergence with the real schema.
   - Proposed: **doc-side fix is the durable home.** The tombstone snippet lives in `docs/account-deletion.md` ("The tombstone user" section) — that's where the next plan to touch tombstones (step 8, the `delete_account` RPC) will look. Add a paragraph there: which `auth.users` columns we rely on, why a bare two-column INSERT works against current GoTrue, and the explicit caveat that bumping the GoTrue image version requires re-validating the insert. The plan can then cross-reference that paragraph in Risks instead of duplicating it.

6. [ ] **Risk #6 is now stale — it claims grants are "verified end-to-end via the smoke check", but the same plan guts the smoke's `/profiles` probe.** After `0010` lands, no smoke-level probe will exercise the grants matrix until step 3 introduces an authenticated probe.
   - Proposed: reword Risk #6 to point at `grants.sql` (the pgTAP file with the 23 assertions including the two load-bearing negatives) as the canonical grants check, and call out step 3 as the future integration-level verification.

7. [ ] **Risk #6 also references "step 14 of the migration ordering" for grants; grants are step 15.** Off-by-one.
   - Proposed: change "step 14" → "step 15" in Risk #6.

8. [ ] **Step 1's smoke-profile DROP guard is framed as "defence-in-depth against an accidental ledger reset", but the rest of the migration won't survive a ledger reset either.** Step 4's `CREATE TABLE public.profiles` would error on a second run, step 5's `CREATE TABLE public.lists` likewise, and so on. The guard prevents accidental data loss on the *first* statement of a re-run, not the reset hazard the framing suggests.
   - Proposed: tighten the framing: the guard's job is solely to prevent destroying a real `profiles` table if `0004` were ever re-run against an already-migrated DB. Ledger-reset re-runs of the whole migration are unsupported by design — the recovery path is `docker compose down -v && up -d && migrate && seed`. State that explicitly so the next reader doesn't try to make `0004` re-runnable.

9. [ ] **`rls_lists.sql`'s "INSERT denied" assertion doesn't split the GRANT-layer denial from the policy-layer denial the way `rls_profiles.sql` does.** `rls_profiles.sql` deliberately tests anon-via-GRANT (`42501`) and authenticated-without-claims-via-RLS as two separate assertions, on the rationale that "RLS without GRANT silently returns empty, and GRANT without RLS would expose every profile". The lists case has the same shape — no INSERT grant *and* no INSERT policy — but only one combined assertion.
   - Proposed: **plan-side fix, with an optional doc dimension.** Plan-side: split the lists "INSERT denied" check into two assertions in the same shape as `rls_profiles.sql` — one `throws_ok` on SQLSTATE `42501` under `authenticated`, and a second covering the missing-policy defence. Adjust `plan(N)` if this changes the count. Doc-side (optional, only if the user wants a durable convention): codify "for tables with both no-GRANT and no-policy defences, test each layer separately" in `docs/testing.md` so future plans don't re-conflate them.

10. [ ] **`infra_auth_stub.sql`'s plan(4) and prose don't quite agree.** The description enumerates five distinct things ("bootstrap created `auth.users`", `has_function('public','uid')`, gated `public.uid()` return value, tombstone row exists, fixture include works) but the count is 4. The intent is that `has_function` is the `skip_unless` predicate, not its own assertion — but the prose reads like both at once.
   - Proposed: clarify the prose so `has_function` is described purely as the gate (no `ok()` of its own), and the four assertions are: auth.users-table-exists, gated `public.uid()`-returns-claim-uid, tombstone-row-exists, fixture-include-works. Or, if `has_function` *is* its own assertion, bump plan(4) → plan(5).
